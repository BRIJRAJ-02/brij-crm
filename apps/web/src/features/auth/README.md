# Sign in

Spec 0005, milestone 1, redesigned by spec 0036. Sign in, the code page and the second step sit in `AuthLayout`'s split card beside the empty sketch (`signInFrame`), so the card holds still from the first page to first run (design sweep, 22 October 2026: the second step was the narrow card, and the card jumped); everything they send goes through `data.auth`.

## `/sign-in` (SignInScreen)

- **Purpose**: one way in for everyone, new or returning: Google (where the API says it is on), or a code sent to an email. The server decides whether it signs in or signs up.
- **Main task**: Continue with Google, then "or", then type an email and press Continue with email: the code goes out and the page moves to `/verify`.
- **Leaves out**: passwords, passkeys (taken out 22 October 2026, the owner: "remove passkey right now not needed"), a separate sign up page, account settings.

## `/verify` (VerifyScreen)

- **Purpose**: prove the email is yours with the 6 digit code sent to it.
- **Main task**: type or paste the code (checked as soon as it is complete), then go on to `?redirect=` or `/`.
- **Leaves out**: editing the address here ("Use a different email" goes back, in one click) and other sign in methods. Spec 0033's second step gets its own page at `/sign-in/two-factor`.

## Notes

- `?redirect=` is honoured only for a path in the app (`safeRedirect`: resolved against the app's origin, it must stay on it, its path can't start with `//`, and it can't be a sign in page, compared lowercase after undoing escapes).
- A refused send that is about the address (not an email) marks the email field; any other (sign up closed, too many codes, the server down) is about signing in and shows at the top of the card, never as a red field (`isAboutAddress`).
- `?error=` on `/sign-in` is a refused Google sign in; the form says it in the page's words (`googleRefusal`), never the code itself. `?signedOut=ended` or `unsaved` is a session that ended under the person (a 401 mid use, from the data layer's `onSignedOut`); the form says so above the fields, `unsaved` adding that the last change wasn't saved. Both leave the address once read, so a reload doesn't say them again. A failure that isn't one of ours reads "Something went wrong", never the thrown value.
- The address the code went to and when are kept in this tab's sessionStorage (`pending.ts`), so `/verify` survives a reload; verifying or "Use a different email" clears them. "Use a different email" keeps the address alone, so `/sign-in` starts with it (cleared once a sign in succeeds).
- The resend wait is counted here (`useSecondsLeft`) and passed to VerifyEmail as `resendWait`: 60 seconds after each send, or the server's `Retry-After` after a refused one (`DataError.retryAfterSeconds`). A refused resend shows under "Resend code" (`resendError`), never on the code boxes, and never says "New code sent". A rate limited resend says only "Too many codes sent to this email." (`resendRefusal`): the wait line under the button counts the time, so it isn't said twice.
- Refusals are worded in `messages.ts`: a rate limit gives the real wait ("Try again in 10 minutes."), a closed sign up says so plainly, a wrong code doesn't offer a new one while none can be sent, and a code tried too often, expired or rate limited is spent (the boxes turn off until a new code is sent).
- Back from Google with the browser's back button, "Opening Google" resets (`pageshow`).
- `AuthStates.tsx` holds the loading and failed states the pages before the app share; `AuthPending` and `AuthError` take `isSplit` for the split card, with an empty sketch beside it, which the second step, first run, join and invite pass (their own screen is that card). `AuthError` keeps the page's title and says why in one announced danger Callout (the server's sentence, else "Can’t reach Timefix. Check your connection, then try again."), then a primary full width Try again that spins while the route runs again: no second heading under the title. `/` loads as "Opening Timefix", true whether it then opens a workspace or sign in, and fails as "Can’t open Timefix" with "Check your connection, then try again." under it.
- Which place `/`, `/sign-in` and `/verify` hold while `me.get` is out is `SessionPending`'s, and `SessionError`'s for a failed check (the owner, 24 October 2026: "before checking it flashed the signup page"). A single page app can't know there is a session until that answer comes, so drawing sign in first showed a signed in person the sign up page for a moment. `hint.ts` keeps what the layer last learned for certain (the data layer's `onSessionKnown`, from `me.get`, a session ending and every sign in or out) in localStorage as `crm.session`, `out` or `in:<when>`, an `in` counting for no longer than a session can last (30 days). The hint only picks the place: `in` (and `/`'s default when the browser has never said) holds the app's own loading state, `OpeningApp.tsx`, which stands where the workspace frame will; `out` (and the sign in pages' default) holds sign in's own frame, so nobody waits on a screen they aren't going to. It is never proof: `me.get` always decides, and nothing of anyone's is read or shown on the strength of it. `parent-hint.ts` is its cross host cousin (25 October 2026, the owner: "if I am already logged in and I go to timefix.com, it should just detect and take me to the dashboard"): the same answer writes `tf_signed_in=1` on the public booking host the app's own host sits under (`timefix.com`, and no other pair of hosts gets a cookie at all), `Secure`, `SameSite=Lax`, for no longer than a session can last, and clears it whenever nobody is signed in. It carries no identity, no token and no email, only presence and an expiry, because every host under that domain can read it. `apps/web/middleware.ts` reads it on the apex's home alone, to send a signed in person to the app rather than the marketing site; `?stay=1` on that address keeps the marketing site. Outside production there is no parent domain to write on (one host serves both), so nothing is written. `OpeningApp` says "Still opening Timefix" with Try again after five seconds, so a hung call is never a silent spinner.
- `SignOutDialog.tsx` is the confirm the pages before the app ask with before signing out (the owner's rule of 21 October 2026): a plain Modal, "Sign out?", "You’ll need to sign in again on this device.", Cancel (ESC) first and a primary Sign out last that spins while it runs and runs once; a failure shows inside it. First run uses it; it matches the workspace menu's (spec 0031).

## Second step (`/two-factor`, TwoFactorScreen)

- **Purpose**: a sign in held back because two factor is on (spec 0033, AC-882, AC-884): an email code or Google proved the email, not yet the person.
- **Main task**: type the authenticator app's 6 digit code (it sends itself once complete) or, after "Use a backup code", one of the backup codes ("Use a backup code" and back, a full width ghost button under Continue, as a Form's other ways to go on are); "Remember this device for 30 days" sits above the code so it is never skipped. A footer link, Use a different email (as /verify words it), goes back to /sign-in keeping `?redirect=`, and is off while a code is being checked. A wrong code says so under the field and focus returns to it; a run out or over tried sign in says the server's sentence in a warning Callout with a primary full width Sign in again under it (keeping `?redirect=`).
- **Leaves out**: any way round the second factor (no email recovery, owner decision).

The pending sign in lives in Better Auth's HttpOnly cookie, so the page can't tell a stale one: the server says so. VerifyScreen goes here when `auth.verify` answers `second-step`; Google's callback redirects here.
