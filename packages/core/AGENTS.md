# packages/core

## Overview

The domain services the api and the worker share, and (from Access model, #9) the one access door every read and write passes. No HTTP lives here. Tagged `server`.

## Key files

| File | Owns |
|---|---|
| `src/index.ts` | The package's public services |
| `src/system/status.ts` | The pattern to copy: a deps interface plus one service function |
| `src/milestones/milestones.ts` | The milestones a workspace reaches once (spec 0010, AC-177): `reachMilestone` stores one in the write's transaction, `milestoneHook` reaches `first_record_created` for a member's first record. Core only returns what a write reached; the api sends the events |

| `src/emails/` | Queued email (the emails lane). `queue.ts`: `queueEmails(tx, inputs)` in the caller's transaction, in two statements however many (one insert, then `crm_enqueue_email` per new row, ids only, on the workspace's own `email:<workspace>` queue, 11 tries), each answered in order as `{ outcome: 'queued' | 'exists', emailId }` or `{ outcome: 'refused', code: 'PARAMS_INVALID' }` (params checked by the kind's schema in `@crm/contracts/emails`, an address by its loose `EmailAddress`; a refusal is never thrown, so the caller's change commits). The key is `<kind>:<ids>`, ids only, unique per workspace. `queueEmail` is one of them, with one typed function per queued kind (`queueFormSubmissionNotice`, `queueFormConfirmation`, `queueCalendarDisconnected`, `queueBookingCalendarRemoved`, `queueImportFinished`; a mention has no queued kind: it is emailed once, in the notifications email of spec 0038). `send.ts` (system, the worker's `crm_email` task): `loadEmail` (the reader's address read now: a removed member, a topic turned off, or an email queued more than 24 hours ago is a skip) and `finishEmail` (sent, skipped, failed or a counted retry; a finished one has its params and address blanked). `preferences.ts`: an optional email's signed tokens (`emailLinkToken`, `readEmailLinkToken`: a workspace, a member and a topic, a year, the key passed in), one per purpose, neither reading as the other: `page` (every topic) and `unsubscribe` (the one click, whose address request logs keep: its own topic off only) and the member's choices (`readEmailPreferences`, `setEmailPreference`, which keeps `updated_via`) under the narrow scope the door's `enterEmailLink` mints: an `email_link` principal with no permission, which no member service takes. Calendar sync queues `calendar_disconnected` when a connection turns `expired` or `failed` (once a spell and reason), and the sync that cancels a booking whose event its host deleted queues the host's `booking_calendar_removed` (the guest gets nothing). The daily cleanup (`emails` phase) ends an email still queued after a day `failed` (`queue_lost`) and deletes emails older than 30 days |
| `src/views/` | Saved views (spec 0020): `seed.ts` (each object's default view, written by `insertObject`), `views.ts` (`listViews` in switcher order, `getView` with hidden columns cut, `saveViewQuery` under the view's row lock with its `VIEW_CHANGED` version check, the lock rule and `checkViewQuery`; every refusal for a view the caller can't see is one `NOT_FOUND`), `facts.ts` (`viewFacts`, the relay's read for spec 0009's `views` rule, system only, in `@crm/core/system`). A save records `Change.views`, so `outboxHook` stores one `views` row per object. `manage.ts` (milestone 2): `createView` (replay by id, limits, `NAME_TAKEN` on `name`), `updateView`, `setViewLayout` (`mergeLayout` keeps what the writer can't see), `moveView`, `setViewLocked`, `setDefaultView`, `deleteView`, `markViewOpened` (`member_view_state`, no outbox row) and `deleteMemberViews` (called by `removeMember`); who may do what is `viewRule` from `@crm/contracts/views`; object then view, both locked `for no key update` |
| `src/reports/` | Saved reports (the reports lane, spec 0050 reserved): `reports.ts` (`listReports`, `createReport` with replay by id and `ID_TAKEN`, `updateReport`, `deleteReport`; every config is checked by `reportProblem` and its filter compiled by `checkViewQuery` before it is stored; a report is listed only to a reader who can read its object and see every field its measure, group by and filter name, so a hidden field's name or value never reaches them; its maker or a holder of `views.manage` changes or deletes it, anyone else is `FORBIDDEN`; 200 a workspace, `limits.reportsPerWorkspace`). A definition holds no records, so these writes store no outbox row |
| `src/availability/` | Availability schedules (spec 0035): `resolve.ts` (`defaultSchedule`, `scheduleFor`, `resolveMany`: a named schedule of the member's, else their stored default, else the virtual default in the caller's zone; `loadPage` and the page views resolve through it in one query, a page carrying its schedule's name) and `schedules.ts` (`listScheduleMembers`, whose schedules the reader may view: the Viewing Select's one service; list, get (an owner or admin sees every page using it; a colleague reading through a page they book on sees only those), create (a member's first schedule stores their virtual default beside it, so they keep one default), update with the `STALE` check, set default, duplicate, delete repointing pages to the default, `checkPageSchedule` for `SCHEDULE_NOT_ALLOWED`, and the default's hours behind `bookings.hours` and `setHours`); every write goes through `writeSchedules`, takes the member's schedules lock and records `Change.schedules`, one `schedules` outbox row, then hands what it changed to `afterScheduleChange` (empty: spec 0037's audit row and member notice attach there, AC-1444); colleagues go through `canActFor` over the reach (`src/access/scheduling.ts`, spec 0037's one scheduling check; today `booking.admin` reaches everyone): outside See a member answers as absent, Seen but not Managed a write is FORBIDDEN; `mayEditOwnHours` holds the own check |
| `src/teams/` | Teams (spec 0031, slice 8, AC-824 to AC-827): flat groups of members that access rules name. `teams.ts` (`listTeams`, `createTeam` with an optional client chosen UUID v7 so an Undo of a delete brings the same team back, `renameTeam`, `deleteTeam` refused `IN_USE` while an access rule, a record rule or a scheduling delegation names the team, and `changeTeamMembers`, the one place who is in a team changes: idempotent adds and removes under the team's row lock, active members only, one `team.changed` audit row and the `members` and `access` outbox rows in the same transaction) and `teamsRemoval` (a removed member leaves their teams). `reach.ts` (`membersAffectedByTeamChange`): which members the `access` row names after a membership change, today the people who joined or left and the team's other members (a `team` record rule shows each of them different records); spec 0037 (AC-1274) extends it with the delegates whose scheduling reach runs through the team. `teams.manage` is checked before any input is read |
| `src/access/rules.ts`, `stored-rules.ts`, `rule-guard.ts` | Access rules by role and team (spec 0032, milestones 1 and 3). `stored-rules.ts`: `storedRules`, the production `RuleSource` (the api's `APP_RULES`): in the door's one statement it reads the member's teams, the active members of those teams (for a `team` record rule) and the stored `access_rules` and `record_rules` naming their role or one of their teams; `workspaceRules` is the relay's read of the same for every member, so the audiences group members by equal policies. `policy.ts` combines them (AC-844): a member's views are their role's (its rule, else write) and each team's (its rule, else nothing: a team only grants); the most open object level wins, a field's most open level across the views that see the object, and the broadest record scope (any view without a record rule makes the object whole); a stored level or kind the code doesn't know makes that view none; a result that restricts nothing is the open policy (and audience), and owners and admins keep it, since no stored rule can name them. `rules.ts`: `getObjectAccess` and `setObjectAccess` (`access.manage`): the Member role (edit all records is its default, so stored as no rule) and teams (a team with no access is no row), a level and a record scope per subject; `own` and `team` read the object's Owner field (`ownerAttributeOf`) and are refused without one; a repeat writes nothing; one `access.rule_set` audit row and one `access` row naming the members the subject covers. `rule-guard.ts`: an Owner field a record rule reads can't be archived (`IN_USE`), and `outOfScopeMessage` (a write that handed a record to someone its writer can't see saves, then answers `RECORD_OUT_OF_SCOPE` with "Saved. It's owned by Grace Hopper, so you can no longer see it.", from `editRecord`, `editRecords` and `addRecord`). A record made by a member under a record rule is theirs (`creatorOwns` in `engine/records.ts`, AC-848). Field rules (milestone 2, AC-846, AC-850): a subject's `rule` may carry `fields` (read only or hidden per attribute, stored as `access_rules` rows with an attribute; left out they stay, `null` clears them); the policy already reads them, so the door hides or locks a field in every read, write, filter, sort, export and event with no code of its own. A field must be a live one of this object, the record's name is never hidden (`CONFIG_INVALID`), a level the code doesn't know reads as hidden. Every record rule of an object reads the one field the first was made with (the tab names it), so an Owner field made later never splits them. `setObjectAccess` answers `{ access, impact }`: `impactOf` runs the covered members' policies before and after from `workspaceRules` (so it is the door's own function) and counts who lost a level, records or a field, the shared views naming a field they lost (all of the object's when the object went) and the live forms filing onto one. `preview.ts` (`previewAccess`, AC-858) shows an object as a member, or a Member in a team, would see it: `previewScope` in `door.ts` mints a scope on the previewer's actor with that person's policy, only reads go through it (fields, count, first names), and one `access.previewed` audit row is its only write |
| `src/roles/` | Custom roles (spec 0037, job J9): `roles.ts` (`listRoles`, what every role picker offers, custom roles after the built in ones with the default for new people; `roleOverview` and `getRole`, every role's permissions, data access and holders for Settings › Roles, a guest getting names only; `createRole`, `updateRole` (`STALE` against `updatedAt`; one `role.updated` audit row with the permissions added and removed; one `access` row naming the holders when what they can do changed), `duplicateRole`, `deleteRole` (moves holders and open invitations to Member or another custom role in the same transaction), `setDefaultRole`, `moveRole`, all `access.manage`; names 1 to 40, never a built in role's (`ROLE_NAME_RESERVED`), only grant `any` permissions (`PERMISSION_NOT_ALLOWED`), at most 20 under the `roles:<workspace>` advisory lock (`ROLE_LIMIT`)). The door reads a member's custom role in their own statement (`CUSTOM_ROLE_COLUMNS` and `customRoleJoin` in `access/door.ts`), and `roleAccess` keeps its stored permissions to grant `any` ones and takes its data access as the default object level; Member's rules never apply to a custom role holder. Who holds one changes in `members/members.ts` (`setMemberRole` with `customRoleId`, `setMemberRoles` for several) |
| `src/audit/` | Settings › History › Workspace changes (spec 0046): `audit.ts` (`listAuditEvents`, `audit.read` checked before any read; one transaction under a 3 second statement timeout: the page in `audit_events_at`'s order, `at desc nulls last, id asc` (so the index gives it with no sort; an EXPLAIN test holds it), keyset paged on `at` kept as Postgres's text to the microsecond and the id, only the listed actions, never `ip` or `request_id`; then one `union all` statement naming the members, invitations (no address once the member it made deleted their account), requests, round robins, forms, booking pages and bookings the page mentions, skipped when it names nothing; 4 statements a page, 3 when empty; writes nothing) and `view.ts` (`toEntryView`, pure: a row and its names into a strict `AuditEntryView`, only each action's known keys, a linked record never read, a deleted account's profile fields named without values) |

## Conventions

- A service is a function that takes its dependencies (`{ db, environment }`) and its input, and returns a type from `packages/contracts`.
- One folder per feature (`src/<feature>/`), exported through `src/index.ts`.
- Never import Hono, `@orpc/server` or `process.env`. The api and the worker pass in everything a service needs.
- Tenant data is read and written only through `db.withWorkspace()`, and (from #9) only with a scope the access door produced. See `crm-data-model-access`.
