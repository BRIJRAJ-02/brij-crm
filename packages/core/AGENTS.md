# packages/core

## Overview

The domain services the api and the worker share, and (from Access model, #9) the one access door every read and write passes. No HTTP lives here. Tagged `server`.

## Key files

| File | Owns |
|---|---|
| `src/index.ts` | The package's public services |
| `src/system/status.ts` | The pattern to copy: a deps interface plus one service function |
| `src/milestones/milestones.ts` | The milestones a workspace reaches once (spec 0010, AC-177): `reachMilestone` stores one in the write's transaction, `milestoneHook` reaches `first_record_created` for a member's first record. Core only returns what a write reached; the api sends the events |
| `src/validation/` | Validation rules (spec 0013): `rules.ts` writes an attribute's rules (replace semantics, `rule_count` and `rules_version` kept exact, the 20 rule limit) and checks the rules a record write touches under its lock (`checkRecordRules`); `pattern.ts` is the only server file that imports `re2js`; `bypass.test.ts` places every engine export and fails when a new write skips the rules |
| `src/emails/` | Queued email (the emails lane). `queue.ts`: `queueEmails(tx, inputs)` in the caller's transaction, in two statements however many (one insert, then `crm_enqueue_email` per new row, ids only, on the workspace's own `email:<workspace>` queue, 11 tries), each answered in order as `{ outcome: 'queued' | 'exists', emailId }` or `{ outcome: 'refused', code: 'PARAMS_INVALID' }` (params checked by the kind's schema in `@crm/contracts/emails`, an address by its loose `EmailAddress`; a refusal is never thrown, so the caller's change commits). The key is `<kind>:<ids>`, ids only, unique per workspace. `queueEmail` is one of them, with one typed function per queued kind (`queueFormSubmissionNotice`, `queueFormConfirmation`, `queueCalendarDisconnected`, `queueBookingCalendarRemoved`, `queueImportFinished`, `queueMention`). `send.ts` (system, the worker's `crm_email` task): `loadEmail` (the reader's address read now: a removed member, a topic turned off, or an email queued more than 24 hours ago is a skip) and `finishEmail` (sent, skipped, failed or a counted retry; a finished one has its params and address blanked). `preferences.ts`: an optional email's signed tokens (`emailLinkToken`, `readEmailLinkToken`: a workspace, a member and a topic, a year, the key passed in), one per purpose, neither reading as the other: `page` (every topic) and `unsubscribe` (the one click, whose address request logs keep: its own topic off only) and the member's choices (`readEmailPreferences`, `setEmailPreference`, which keeps `updated_via`) under the narrow scope the door's `enterEmailLink` mints: an `email_link` principal with no permission, which no member service takes. Calendar sync queues `calendar_disconnected` when a connection turns `expired` or `failed` (once a spell and reason), and the sync that cancels a booking whose event its host deleted queues the host's `booking_calendar_removed` (the guest gets nothing). The daily cleanup (`emails` phase) ends an email still queued after a day `failed` (`queue_lost`) and deletes emails older than 30 days |
| `src/views/` | Saved views (spec 0020): `seed.ts` (each object's default view, written by `insertObject`), `views.ts` (`listViews` in switcher order, `getView` with hidden columns cut, `saveViewQuery` under the view's row lock with its `VIEW_CHANGED` version check, the lock rule and `checkViewQuery`; every refusal for a view the caller can't see is one `NOT_FOUND`), `facts.ts` (`viewFacts`, the relay's read for spec 0009's `views` rule, system only, in `@crm/core/system`). A save records `Change.views`, so `outboxHook` stores one `views` row per object. `manage.ts` (milestone 2): `createView` (replay by id, limits, `NAME_TAKEN` on `name`), `updateView`, `setViewLayout` (`mergeLayout` keeps what the writer can't see), `moveView`, `setViewLocked`, `setDefaultView`, `deleteView`, `markViewOpened` (`member_view_state`, no outbox row) and `deleteMemberViews` (called by `removeMember`); who may do what is `viewRule` from `@crm/contracts/views`; object then view, both locked `for no key update` |
| `src/availability/` | Availability schedules (spec 0035): `resolve.ts` (`defaultSchedule`, `scheduleFor`, `resolveMany`: a named schedule of the member's, else their stored default, else the virtual default in the caller's zone; `loadPage` and the page views resolve through it in one query, a page carrying its schedule's name) and `schedules.ts` (`listScheduleMembers`, whose schedules the reader may view: the Viewing Select's one service; list, get (an owner or admin sees every page using it; a colleague reading through a page they book on sees only those), create (a member's first schedule stores their virtual default beside it, so they keep one default), update with the `STALE` check, set default, duplicate, delete repointing pages to the default, `checkPageSchedule` for `SCHEDULE_NOT_ALLOWED`, and the default's hours behind `bookings.hours` and `setHours`); every write goes through `writeSchedules`, takes the member's schedules lock and records `Change.schedules`, one `schedules` outbox row, then hands what it changed to `afterScheduleChange` (empty: spec 0037's audit row and member notice attach there, AC-1444); colleagues go through `canActFor` over the reach (`src/access/scheduling.ts`, spec 0037's one scheduling check; today `booking.admin` reaches everyone): outside See a member answers as absent, Seen but not Managed a write is FORBIDDEN; `mayEditOwnHours` holds the own check |

## Conventions

- A service is a function that takes its dependencies (`{ db, environment }`) and its input, and returns a type from `packages/contracts`.
- One folder per feature (`src/<feature>/`), exported through `src/index.ts`.
- Never import Hono, `@orpc/server` or `process.env`. The api and the worker pass in everything a service needs.
- Tenant data is read and written only through `db.withWorkspace()`, and (from #9) only with a scope the access door produced. See `crm-data-model-access`.
